# Первый запуск в интернете

Этот документ относится к **новому отдельному** проекту. Не выполняй миграции в базе магазина или бота.

## 1. Подготовить Supabase

Создай новый проект `neo-fit` в выбранной тобой организации и регионе, предварительно проверь тариф и возможную стоимость. Пароль базы сохрани у себя. Он не нужен в исходниках сайта и не должен отправляться в чат.

В SQL Editor нового проекта выполни файл `supabase/migrations/202609160001_diary.sql`. Он создаёт только две таблицы дневника, политики RLS и функцию `save_diary`. Не отключай RLS и не заменяй защищённую запись прямыми обновлениями таблицы из браузера.

Скопируй **Project URL** и **publishable key** из настроек проекта. Для локальной облачной сборки создай `.env` по `.env.example`. В браузерном приложении разрешён только publishable/legacy anon key. `service_role`, `sb_secret_*` и пароль базы в `.env` сайта, JSON-конфигурации и GitHub Variables запрещены.

## 2. Регистрация и вход

Создай Edge Function `diary-register` из `supabase/functions/diary-register/index.ts`. В её серверных Secrets задай:

```text
ALLOWED_ORIGIN=https://ИМЯ_АККАУНТА.github.io
AUTH_DOMAIN=users.neo-fit.invalid
```

`ALLOWED_ORIGIN` — только origin без `/neo-fit/` и без завершающего слеша. Для собственного домена используй его HTTPS-origin. Для временной проверки локального облачного входа используй точный origin локального сервера и после теста верни публичный origin. Несовпадающий origin не сможет зарегистрировать аккаунт.
Для этого репозитория в функции уже есть безопасный публичный fallback
`https://upneo.github.io`; Secret нужен только при смене домена.

`DIARY_INVITE_CODE` можно задать там же, но штатная поставка хранит
приглашение в Supabase Vault под именем `neo_fit_diary_invite`. Оно создаётся
случайно на сервере и не проходит через Git, браузерную сборку или журналы.
Владелец может прочитать его в SQL Editor своего проекта:

```sql
select decrypted_secret
from vault.decrypted_secrets
where name = 'neo_fit_diary_invite';
```

Не включай результат в репозиторий и не используй приглашение как пароль аккаунта. Supabase предоставляет `SUPABASE_URL` и `SUPABASE_SECRET_KEYS` внутри своей серверной среды. Legacy `SUPABASE_SERVICE_ROLE_KEY` поддерживается только как переходный fallback. Не копируй secret/service key в браузер.

Функция регистрации сама проверяет секрет приглашения; поэтому в `supabase/config.toml` именно для неё стоит `verify_jwt = false`. Это не отключает проверку пользовательского JWT для таблиц/RPC. Не выставляй такой параметр другим функциям без собственного механизма авторизации.

Через установленный Supabase CLI можно выполнить:

```sh
supabase login
supabase link --project-ref <REF_НОВОГО_ПРОЕКТА>
supabase secrets set --env-file supabase/secrets.env
supabase functions deploy diary-register
```

`supabase/secrets.env` создаётся вручную по `secrets.example.env`, исключён из Git. SQL выше можно применять через Dashboard; CLI-команды не обязаны заменять этот способ.

В Auth оставь вход Email/Password, а свободную публичную регистрацию через обычный Auth signup отключи: новых пользователей создаёт серверная функция по приглашению. Она подтверждает технический адрес сама. Адрес `<логин>@users.neo-fit.invalid` — внутренний идентификатор, не реальная почта. Восстановление пароля по письму в этой версии **не работает**. Забытый пароль восстанавливает владелец через административный интерфейс Supabase; это не обычная email-регистрация.

## 3. Загрузить в новый GitHub-репозиторий

Создай отдельный репозиторий `neo-fit` или `workout-diary`. Для публичного репозитория выкладывай только код проекта. В ZIP нет личной истории, но не добавляй её сам позднее.

Для корректной отправки вложенных и скрытых файлов удобнее Git или GitHub Desktop, а не загрузка ZIP как одного файла. Репозиторий должен содержать `package.json`, `src/` и `.github/workflows/pages.yml` непосредственно в корне.

Перед первой отправкой проверь содержимое `git diff --cached --name-only`. Личных JSON, старого HTML, `.env`, `secrets.env` там быть не должно.

В Settings → Secrets and variables → Actions → **Variables** добавь:

```text
SUPABASE_URL=https://<PROJECT_REF>.supabase.co
SUPABASE_PUBLISHABLE_KEY=<PUBLISHABLE_KEY>
```

Это публичные параметры фронтенда. Секрет приглашения хранится только в Supabase, не в Variables сайта.

В Settings → Pages выбери **GitHub Actions**. После отправки в `main` workflow запустит `check`, `test`, обязательную облачную сборку и публикацию. Если базовые параметры не заданы, сборка остановится с объяснением, а не опубликует ложный облачный вход.

После успешного Deploy реальный адрес будет указан GitHub в Environment `github-pages`. Сам по себе архив не создаёт этот адрес.

## 4. Альтернативная загрузка локальным помощником

Владелец может использовать `npm run publish:github` в распакованном проекте. Предварительно должны быть установлены Git, GitHub CLI и выполнен `gh auth login` с разрешением отправлять workflow. Пароль или токен в команду проекта вручную не подставляется.

Скрипт показывает аккаунт и имя **нового публичного** репозитория, спрашивает «ДА», не перезаписывает существующий репозиторий и отправляет разрешённые папки по списку. Если `.env` уже заполнен publishable-параметрами, передаст их в Variables. Может потребоваться включить Pages через интерфейс, если GitHub отклонит административный вызов. Скрипт не создаёт и не оплачивает Supabase.

## 5. Проверить реальные права доступа

Создай два тестовых аккаунта с разными логинами. В первом запиши подход; открой второй в другом браузере: записи первого не должны появляться. Анонимный вызов таблиц и неавторизованный RPC должны быть запрещены. Прямое изменение `user_id` не должно позволять доступ к чужому документу.

Для отдельного тестового проекта предусмотрен `supabase/tests/diary_rls.test.sql` с pgTAP. Он использует транзакцию/rollback и синтетических пользователей. Эти тесты **не выполнялись на твоём облаке** при подготовке ZIP. Сначала проверь их на отдельной тестовой базе, а не поверх настоящих записей.

Проверь на двух устройствах: вход в один профиль, сохранение, повторное чтение, режим без сети в уже открытой вкладке, восстановление соединения и конфликт одновременных изменений. При конфликте сохрани свою JSON-копию перед загрузкой другой версии.

## 6. Перенести личную историю

Создай свой аккаунт `Neo`, аккаунт Вики `vikusia`, выбери стартовые программы. Пароли задаются при регистрации; в проекте их нет. Затем в нужном профиле один раз импортируй личный зашифрованный JSON, выданный отдельно. В нём выбирай соответствующий старый профиль.

Для полностью нового аккаунта подходит «Полное восстановление». Для аккаунта с уже введёнными новыми тренировками — «Импорт и объединение» плюс осознанный выбор замены программы. Дождись статуса «Сохранено в облаке». Дальше после тренировок ничего скачивать не требуется.
